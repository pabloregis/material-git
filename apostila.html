Preparar o ambiente

Neste treinamento todo mundo usa o mesmo ambiente: o GitHub Codespaces, um editor de código completo que roda no navegador (o VS Code), com terminal e Git já instalados. Você não instala nada, e o que funciona para um funciona para todos.

  1. Crie uma conta gratuita no GitHub e confirme o e-mail. Anote seu nome de usuário e entregue ao instrutor.
  2. Crie o repositório que vai abrigar o seu Codespace. Em github.com/new, dê o nome codespace-aula, deixe como Public (público), marque Add a README file (adicionar um arquivo de apresentação) e clique em Create repository (criar repositório). O Codespace precisa de um repositório com pelo menos um commit, e o README é esse commit.
  3. No repositório, clique no botão verde Code (código) › aba Codespaces › Create codespace on main (criar codespace na main). Em cerca de um minuto, o editor abre no navegador.
  4. Opcional: deixe o editor em português. Abra o menu ☰ › View › Command Palette (paleta de comandos), digite Configure Display Language (configurar o idioma de exibição) e escolha Português (Brasil). Se o idioma não mudar, siga em inglês: a apostila traz a tradução dos nomes.

Para conferir, quando o Codespace abrir, abra o terminal dele (ele costuma já vir aberto embaixo; se não, use o ícone ☰ no alto à esquerda › Terminal › Novo Terminal. O atalho de teclado para abrir um terminal não funciona no Codespace do navegador) e rode:

git --version   # version = versão: mostra a versão do Git instalada

Se aparecer algo como git version 2.47.1, está pronto.

Como o Codespace funciona

Ele para sozinho depois de 30 minutos sem uso, mas guarda tudo o que você fez. Para voltar, abra github.com/codespaces e clique no seu Codespace. A conta gratuita dá horas de uso de sobra para o treinamento.

Configure seu nome e e-mail

O Git grava seu nome e e-mail em cada commit. Use o mesmo e-mail da sua conta do GitHub. A configuração fica guardada dentro do seu Codespace. O Codespace não traz nome nem e-mail: você digita os dois. Se criar outro Codespace, refaça.

Primeiro, digite as duas linhas abaixo, uma de cada vez, com o seu nome e o seu e-mail no lugar dos exemplos, e aperte Enter depois de cada uma:

git config --global user.name "Seu Nome"                # config = configuração; user.name = nome do usuário
git config --global user.email "seu-email@exemplo.com"  # user.email = e-mail do usuário

Depois, copie e cole estas três, que são iguais para todo mundo:

git config --global init.defaultBranch main             # a branch padrão (default) se chama main
git config --global core.editor "code --wait"           # editor = o Git abre o editor quando precisar de um texto
git config --global pull.rebase false                   # pull = puxar: ao puxar, junta as mudanças com merge (mesclar)

Para conferir, rode git config --global user.name: deve aparecer o seu nome, e não “Seu Nome”.

--global (global) quer dizer que a configuração vale para todos os repositórios deste Codespace. A linha do core.editor evita que o Git abra o Vim, um editor de terminal difícil de fechar para quem nunca usou. Se ele abrir mesmo assim, aperte Esc, digite :wq e aperte Enter para salvar e sair. A linha do pull.rebase diz ao Git como juntar o seu trabalho com o do GitHub quando os dois mudaram; sem ela, o git pull pode parar com Need to specify how to reconcile divergent branches (“é preciso dizer como reconciliar branches que divergiram”).

Conceitos

As três áreas do Git, e o GitHub

No seu Codespace, todo arquivo passa por três lugares antes de virar histórico: a pasta de trabalho, a preparação e o repositório local. O GitHub é uma quarta parada, fora do Codespace, para onde o histórico vai quando você o envia:

Pasta de trabalhoOs arquivos que você edita no editor.git add →
Área de preparaçãoO que vai entrar no próximo commit. Em inglês, stage.git commit →
Repositório localO histórico de commits no seu Codespace.git push →
GitHubO repositório remoto, que o time compartilha.← git pull

Quando estiver em dúvida, rode git status (status = situação). Ele diz em que área cada arquivo está e qual comando usar em seguida.

Como ler os comandos desta apostila

Tudo depois de # é um comentário com a tradução e o que o comando faz. O terminal ignora o comentário, então você pode copiar o bloco inteiro.

Para colar no terminal do Codespace, o atalho Ctrl+V não funciona: clique com o botão direito do mouse no terminal e depois no botão Paste (colar) que aparecer. Se o git log ou o git diff encherem a tela e o terminal mostrar : ou (END) (fim) e parar, aperte q (de quit, sair).

Exercício 1 · 28 min

Primeiros commits

Objetivo: criar um repositório com uma página HTML e registrar duas versões dela.

  1. Abra o terminal do Codespace, crie a pasta do projeto e entre nela: 
    cd /workspaces/codespace-aula   # cd = change directory, mudar de pasta: vai para a pasta do seu Codespace
mkdir primeiro-repo            # mkdir = make directory, criar pasta
cd primeiro-repo               # entra na pasta nova
git init -b main               # init = iniciar: transforma a pasta em repositório, com a branch main

    A mensagem Initialized empty Git repository quer dizer “repositório Git vazio iniciado”. A pasta primeiro-repo aparece no Explorador (a barra da esquerda), dentro de codespace-aula. Daqui em diante, os comandos continuam neste terminal. No Explorador, clique com o botão direito em primeiro-repo e escolha New File (novo arquivo) para criar arquivos. Se o terminal sair da pasta, volte com cd /workspaces/codespace-aula/primeiro-repo. Nunca faça commit na pasta codespace-aula: ela só serve de casa para o Codespace.

  2. No editor, crie o arquivo index.html com este conteúdo, trocando pelo seu nome, e salve com Ctrl+S: 
    <!doctype html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <title>Página da Ana</title>
</head>
<body>
  <h1>Olá, eu sou a Ana</h1>
  <p>Estou aprendendo Git.</p>
</body>
</html>
  3. Veja o que o Git percebeu: 
    git status   # status = situação: o que mudou e o que está preparado

    A saída começa com On branch main (“na branch main”) e No commits yet (“ainda sem commits”). O arquivo aparece em vermelho, em Untracked files: “arquivos não acompanhados”. O Git vê o arquivo, mas ainda não guarda as versões dele.

  4. Coloque o arquivo na área de preparação e confira de novo: 
    git add index.html   # add = adicionar: põe o arquivo na preparação
git status           # agora em verde, em "Changes to be committed": mudanças prontas para o commit
  5. Faça o primeiro commit: 
    git commit -m "Cria minha página"   # commit = registrar; -m = message, a mensagem que explica a mudança

    A resposta 1 file changed, 11 insertions(+) quer dizer “1 arquivo alterado, 11 linhas inseridas”; root-commit é o commit raiz, o primeiro do histórico. Sempre use o -m: sem ele, o Git abre uma aba no editor e o terminal fica parado em Waiting for your editor to close the file... (“esperando você fechar o arquivo no editor”). Nesse caso, escreva a mensagem na primeira linha da aba, salve e feche a aba.

  6. Edite a página: acrescente uma linha logo abaixo do <p>, com algo de que você gosta, e salve com Ctrl+S. 
      <p>Gosto de café e de futebol.</p>
  7. Veja a situação e exatamente o que mudou: 
    git status   # agora mostra "Changes not staged for commit": mudanças ainda não preparadas; modified = modificado
git diff     # diff = difference, diferença: linhas com + entraram, com - saíram

    No fim da saída pode aparecer \ No newline at end of file (“sem quebra de linha no fim do arquivo”). É só um aviso: o arquivo termina sem uma linha em branco. Pode ignorar.

  8. Registre a segunda versão e veja o histórico. 
    git add .                            # o ponto (.) quer dizer "tudo nesta pasta"
git commit -m "Adiciona meus gostos"
git log --oneline                    # log = diário de bordo: o histórico; --oneline = uma linha por commit
  9. Agora estrague a página de propósito: apague a linha do <h1> e salve. Para voltar ao que estava no último commit: 
    git status              # modified: index.html (modificado)
git restore index.html  # restore = restaurar: volta o arquivo ao último commit

    O título volta. O git restore descarta as mudanças que ainda não foram preparadas, e não tem volta: use quando quiser mesmo jogar fora o que fez desde o último commit. Se você já tinha rodado git add, rode antes git restore --staged index.html (tira da preparação) e depois o git restore index.html.

Confira

git log --oneline mostra dois commits, o mais novo em cima, e o título voltou depois do git restore.

O painel Source Control

O primeiro-repo pode aparecer no painel Source Control (controle do código-fonte, o ícone de ramos na barra da esquerda), às vezes com um botão Publish Branch (publicar a branch). Ignore o painel e não clique nesse botão: neste treinamento, tudo é pelo terminal, e o envio para o GitHub fica para o exercício 3.

Boas mensagens de commit

Comece com um verbo e diga o que mudou: Adiciona meus gostos, Corrige o título. Evite ajustes, teste ou asdf: daqui a um mês ninguém vai saber o que foi feito.

Exercício 2 · 30 min

Branch, merge e conflito

Objetivo: trabalhar numa branch (ramo), juntar na main e resolver um conflito.

Parte A: um merge sem conflito

  1. Crie a branch rodape e passe a trabalhar nela: 
    git switch -c rodape   # switch = trocar; -c = create, criar: cria a branch e troca para ela

    O Git responde Switched to a new branch 'rodape': “trocou para uma branch nova, a rodape”.

  2. Acrescente um rodapé antes de </body>, salve e faça o commit: 
      <footer>Feito durante o treinamento de Git.</footer>
    git add .
git commit -m "Adiciona rodapé"
  3. Confira que o commit foi feito e volte para a main. Repare que o rodapé some do arquivo no editor: ele só existe na branch rodape. 
    git status        # tem que dizer "nothing to commit, working tree clean": nada para registrar, pasta limpa
git switch main   # troca para a branch main
  4. Junte a branch na main. O rodapé volta: 
    git merge rodape   # merge = mesclar: traz os commits da rodape para a branch atual

    A saída diz Fast-forward (“avanço rápido”): como a main não mudou desde que a rodape nasceu, o Git só a avançou até o commit do rodapé, sem criar um commit de merge.

Parte B: um conflito de propósito

Um conflito acontece quando duas branches mudam a mesma linha. O Git não escolhe por você: ele marca o trecho e espera sua decisão.

  1. Crie a branch titulo-novo: 
    git switch -c titulo-novo
  2. No editor, troque o texto do <h1> para Oi! Meu nome é Ana, salve e faça o commit: 
    git add .
git commit -m "Muda o título"
  3. Confira e volte para a main: 
    git status        # de novo: "nothing to commit, working tree clean"
git switch main
  4. Troque a mesma linha por outro texto, Bem-vindo à página da Ana, salve e faça o commit: 
    git add .
git commit -m "Muda o título na main"
  5. Tente juntar: 
    git merge titulo-novo

    O Git avisa o conflito:

    Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

    Em português: “Mesclando automaticamente o index.html. Conflito de conteúdo no index.html. A mesclagem automática falhou; corrija os conflitos e faça o commit do resultado.” Se rodar git status agora, o arquivo aparece em Unmerged paths (“arquivos não mesclados”) como both modified (“modificado nos dois lados”).

  6. Abra o index.html. O trecho em conflito aparece assim: 
    <<<<<<< HEAD
  <h1>Bem-vindo à página da Ana</h1>
=======
  <h1>Oi! Meu nome é Ana</h1>
>>>>>>> titulo-novo

    Em cima está a versão da main. HEAD quer dizer “cabeça”: é onde você está agora. Embaixo, a versão da branch que chega.

  7. Escolha uma versão, ou escreva uma terceira, e apague as três linhas de marcação. Salve. Quer treinar os dois jeitos? Antes do próximo passo, rode git merge --abort, repita o git merge titulo-novo e resolva agora pelos botões do editor (veja o quadro abaixo).
  8. Conclua o merge: 
    git add index.html                  # avisa ao Git que o conflito está resolvido
git commit -m "Junta o título novo"
git log --oneline --graph --all     # --graph = desenha as branches; --all = mostra todas

No editor

Acima do conflito aparecem os botões Accept Current Change (aceitar a alteração atual: fica a da main), Accept Incoming Change (aceitar a alteração que chega: fica a da branch que chega) e Accept Both Changes (aceitar as duas). Com o editor em português, eles se chamam Aceitar Alteração Atual, Aceitar Alteração de Entrada e Aceitar Ambas as Alterações. Pode aparecer também o botão Resolve in Merge Editor (resolver no editor de mesclagem), que abre uma tela de três painéis; para hoje, use os botões acima do conflito. A branch atual aparece no canto inferior esquerdo; clique nela para trocar ou criar branches.

Confira

O git log --graph desenha duas linhas que se juntam no commit “Junta o título novo”, e o arquivo não tem mais nenhum <<<<<<<.

Os nomes entre parênteses no log mostram em que commit está cada branch: (titulo-novo), (rodape). (HEAD -> main) quer dizer que você está na main, e ela está nesse commit.

Se der errado

Para desistir do merge e voltar ao estado anterior, rode git merge --abort (abort = cancelar).

O merge não deu conflito? Provavelmente você trocou de branch sem salvar ou sem fazer o commit, e a mudança foi junto para a main. Por isso o git status antes de cada git switch.

No terminal, o nome entre parênteses no fim da linha é a branch atual, como (main). Durante um conflito ele continua (main), sem avisar que há um merge em andamento. Para saber, rode git status: enquanto o merge não terminar, ele fala em Unmerged paths ou em still merging (“ainda mesclando”).

Exercício 3 · 25 min

Publicar no GitHub

Objetivo: enviar o repositório para o GitHub, ver a página no ar e trazer de volta uma mudança feita no site.

  1. No GitHub, clique em New (novo), ou no + do canto superior direito › New repository (novo repositório). Dê o nome primeiro-repo, deixe como Public (público) e não marque a opção de README (Add a README file ou Add README, adicionar um arquivo de apresentação). Clique em Create repository (criar repositório).
  2. Entre no GitHub pelo terminal. O Codespace já está ligado à sua conta, mas só ao repositório codespace-aula; para enviar o primeiro-repo, é preciso fazer o login. Rode: 
    cd /workspaces/codespace-aula/primeiro-repo
unset GITHUB_TOKEN   # unset = desfazer: tira do terminal a chave que só vale para o codespace-aula
gh auth login        # gh = GitHub (CLI); auth login = autenticar, entrar na conta
gh auth setup-git    # setup-git = configurar o Git: faz o git push usar esse login

    Responda às perguntas com as setas e o Enter: GitHub.com; Login with a web browser (entrar pelo navegador); HTTPS; Y para Authenticate Git with your GitHub credentials? (autenticar o Git com as suas credenciais). No meio pode aparecer uma dica que começa com Did you know (“você sabia”): é só informação, siga em frente. O terminal mostra um código de 8 caracteres: copie, aperte Enter, abra o endereço github.com/login/device numa aba nova, cole o código e autorize. Quando o terminal disser Logged in as SEU-USUARIO (conectado como), rode o gh auth setup-git. Ele não mostra nada quando dá certo, mas não pule: sem ele, o push falha mesmo com o login feito. Se abrir um terminal novo, rode o unset GITHUB_TOKEN nele antes do push.

  3. Ligue seu repositório local ao do GitHub e envie os commits, trocando SEU-USUARIO:

    O GitHub mostra o endereço do repositório numa página chamada Quick setup (configuração rápida); deixe marcado HTTPS e copie de lá. Cole o endereço no lugar do exemplo:

    git remote add origin https://github.com/SEU-USUARIO/primeiro-repo.git   # remote add = adicionar remoto, com o nome origin (origem)
    git push -u origin main   # push = empurrar: envia a main para a origin

    O -u (de upstream, “rio acima”) liga a sua main à main do GitHub. Depois disso, basta git push e git pull.

    O GitHub não aceita mais a senha da conta no terminal; é por isso que o login é feito pelo navegador.

  4. Recarregue a página do repositório no GitHub. Os arquivos e os commits estão lá.
  5. Publique a página: em Settings › Pages (configurações › páginas), em Source (origem), deixe Deploy from a branch (publicar a partir de uma branch), que já vem marcado. Escolha a branch main (no lugar de None, nenhuma) e a pasta / (root) (a raiz), e clique em Save (salvar). Depois de um ou dois minutos, a página fica em https://SEU-USUARIO.github.io/primeiro-repo/.
  6. Edite pelo site: abra o index.html no GitHub, clique no lápis (Edit this file, editar este arquivo), mude o texto do rodapé e clique em Commit changes... (registrar as mudanças). Na janela que abre, clique de novo em Commit changes para confirmar. Agora o GitHub tem um commit que o seu Codespace não tem.
  7. Traga a mudança para o seu Codespace: 
    git pull   # pull = puxar: traz os commits novos do GitHub e junta na sua branch
Confira

O rodapé que você mudou no site aparece no editor, e git status diz Your branch is up to date with 'origin/main': “sua branch está atualizada com a origin/main”.

Erros comuns
  • rejected ... fetch first (“recusado: busque antes”): o GitHub tem commits que você não tem. Rode git pull e depois o push. Se o pull abrir uma aba no editor com a mensagem Merge branch 'main'... (“mescla a branch main”), feche a aba para concluir.
  • Missing or invalid credentials (“credenciais ausentes ou inválidas”), seguido de um bloco com ECONNREFUSED e de No anonymous write access (“sem acesso de escrita anônimo”) ou Authentication failed (“falha na autenticação”): o Git ficou sem o seu login. Rode unset GITHUB_TOKEN e gh auth setup-git e tente o push de novo. Se continuar, refaça o gh auth login.
  • Permission to ... denied ou erro 403 (“permissão negada”): o terminal voltou a usar a chave do codespace-aula, o que acontece em todo terminal novo e quando o Codespace reinicia. Rode unset GITHUB_TOKEN e o push de novo.
  • remote origin already exists (“o remoto origin já existe”): o remoto já foi adicionado. Confira o endereço com git remote -v (v = verbose, detalhado: mostra os remotos). Se estiver certo, siga para o push.
  • Repository not found (“repositório não encontrado”): o endereço está errado. Veja com git remote -v e corrija com git remote set-url origin ENDERECO-CERTO (set-url = definir o endereço). Depois, rode o push de novo.

Exercício 4 · 30 min

Seu cartão no mural por pull request

Objetivo: colaborar num repositório da turma do jeito que os times trabalham: branch, push, pull request, revisão, merge e release.

develop e main

Nos exercícios 1 a 3 você trabalhou sozinho, direto na main. Num time, é comum ter duas branches fixas. A develop (desenvolvimento) recebe o trabalho do dia a dia, sempre por pull request. A main (principal) é o que está publicado para os usuários, e só recebe a develop num release (lançamento de uma nova versão). O mural funciona assim: o seu cartão vai para a develop, e o GitHub Pages publica a main. Alguns times não usam a develop e trabalham direto a partir da main; no seu time, pergunte qual é o fluxo.

Antes, aceite o convite para colaborar no repositório mural-da-turma. Ele chega no seu e-mail e em github.com/notifications, com o botão Accept invitation (aceitar convite). Se não achar, abra direto github.com/pabloregis/mural-da-turma/invitations. Pegue com o instrutor o número da sua vaga.

  1. Baixe o repositório da turma. Use o endereço abaixo (se o instrutor passar outro, use o dele): 
    cd /workspaces/codespace-aula   # sai do primeiro-repo e volta para a pasta do Codespace
    git clone https://github.com/pabloregis/mural-da-turma.git   # clone = clonar: baixa uma cópia completa
    cd mural-da-turma

    A pasta mural-da-turma aparece no Explorador. O login do exercício 3 continua valendo; se abrir um terminal novo, rode o unset GITHUB_TOKEN nele.

  2. Crie sua branch, com o seu nome no lugar de SEU-NOME, sem espaços nem acentos (por exemplo, cartao-joao). Cada pessoa precisa de uma branch com nome diferente: 
    git switch develop              # garante que você está na develop (desenvolvimento)
git switch -c cartao-SEU-NOME   # cria a branch do seu cartão a partir da develop e troca para ela
  3. No Explorador, abra a pasta mural-da-turma e clique no index.html para abri-lo. Ache a sua vaga e troque só a linha do <li>. Não apague o comentário <!-- vaga NN -->: é ele que separa a sua linha da do colega e evita conflito. No exemplo abaixo, a linha com - sai e a linha com + entra: não digite os sinais. 
        <!-- vaga 07 -->
-   <li class="vazia">Vaga 07</li>
+   <li><strong>Ana</strong> Gosto de café e de futebol.</li>
  4. Faça o commit e envie a branch, trocando o nome na mensagem e no push: 
    git add index.html
git commit -m "Adiciona o cartão de SEU-NOME"
git push -u origin cartao-SEU-NOME   # envia a sua branch para o GitHub
  5. Abra a página do mural-da-turma no GitHub (recarregue, se já estava aberta) e clique em Compare & pull request (comparar e pedir o merge). No alto da página, confira: base: develop (a branch que recebe) e compare: cartao-SEU-NOME (a que chega). Se o botão não aparecer, use o endereço que o próprio push mostrou, depois de Create a pull request for 'cartao-SEU-NOME' on GitHub by visiting: (“crie um pull request para a sua branch visitando:”). O título já vem com a mensagem do commit. Na descrição, escreva o que você mudou, trocando o número pelo da sua vaga: 
    Preenche a vaga NN do mural com o meu cartão.

    Clique em Create pull request (criar o pull request).

  6. Espere a revisão. O instrutor pode pedir uma mudança (Changes requested, “mudanças pedidas”): nesse caso, edite, faça outro commit e outro git push. O pull request se atualiza sozinho. Não faça o merge do seu próprio pull request: quem faz é o instrutor.
  7. Depois do merge, atualize sua develop: 
    git switch develop
git pull   # traz para o seu Codespace os cartões de todos

    O git switch develop pode dizer Your branch is up to date with 'origin/develop' (“sua branch está atualizada”) mesmo havendo cartões novos. Ele compara com a última vez que o Codespace consultou o GitHub, não com o GitHub de agora. Por isso, rode o git pull sempre.

  8. No fim do exercício, o instrutor faz o release: um pull request da develop para a main. Depois do merge, o GitHub Pages publica a nova versão em um ou dois minutos, em https://pabloregis.github.io/mural-da-turma/.
Confira

Seu cartão aparece no index.html da sua develop, junto com os dos colegas. Depois do release, aparece também no mural publicado. Se o seu pull request teve o merge depois do release, o cartão entra no próximo.

Se der errado
  • Permission to ... denied ou erro 403 (“permissão negada”) no push: você ainda não aceitou o convite do repositório, ou o terminal ainda usa a chave do codespace-aula. Aceite o convite, rode unset GITHUB_TOKEN e o push de novo; se continuar, chame o instrutor.
  • rejected (recusado) no primeiro push da sua branch: outra pessoa já usou esse nome de branch. Troque o nome com git branch -m cartao-OUTRO-NOME (m = move, renomear) e rode git push -u origin cartao-OUTRO-NOME.
  • Fez o commit na develop sem criar a branch? Crie agora com git switch -c cartao-SEU-NOME: o commit vai junto. Depois, envie a branch.
Por que cada um na sua branch

A develop é a versão que todo o time usa. Ninguém envia direto para ela: o trabalho chega por pull request, e alguém revisa antes. Se o seu pull request aparecer com base: main, clique em Edit (editar), ao lado do título, e troque a base para develop. Se duas pessoas mudarem a mesma linha, o GitHub mostra o conflito no pull request antes do merge.

Exercício 5 · 30 min

Frontend e componentes

Frontend é a parte do sistema que o usuário vê e usa. No navegador, toda página é feita de três linguagens, e o mural da turma tem as três:

ArquivoLinguagemPapel
index.htmlHTMLO conteúdo e a estrutura: títulos, parágrafos, listas, botões.
style.cssCSSA aparência: cores, fontes, espaços, a grade dos cartões.
script.jsJavaScriptO comportamento: o botão que sorteia um colega.

As tags (etiquetas, as marcações entre < e >) do HTML também são palavras em inglês: html é a página inteira, head é cabeça (as informações da página), title é o título da aba, meta traz informações extras, body é o corpo (o que aparece na tela), footer é rodapé, h1 é heading (título) de nível 1, p é paragraph (parágrafo), ul é unordered list (lista sem números), li é list item (item da lista), strong é forte (negrito) e button é botão.

Parte A: explore com as ferramentas do navegador

  1. Abra o mural publicado, em https://pabloregis.github.io/mural-da-turma/, e aperte F12. Se o seu cartão ainda não estiver lá, use o de um colega. É o DevTools (ferramentas do desenvolvedor), a ferramenta de inspeção do navegador. Se o navegador perguntar se quer abrir as ferramentas, confirme. Se o navegador estiver em português, as abas podem aparecer como Elementos e Estilos.
  2. Na aba Elements (elementos), clique na seta de seleção e depois na frase do seu cartão (não no nome). O <li> dele aparece destacado; se aparecer o <strong>, clique na linha do <li>, logo acima.
  3. No painel Styles (estilos), ache a regra .cartoes li e mude o background (fundo) para lightyellow (amarelo-claro). A mudança é só no seu navegador: recarregue e ela some.
  4. Na aba Console (console, onde se digitam comandos de JavaScript), digite (sem colar) e aperte Enter. Se colar, o navegador pode mostrar um aviso pedindo para digitar allow pasting (“permitir colar”), uma proteção contra golpes: 
    document.querySelector("h1").textContent = "Mural da melhor turma"

    Em português: “no documento, procure o h1 e troque o texto dele”.

Parte B: o problema da repetição

Abra o index.html do mural no editor. O mesmo cartão está escrito 30 vezes. Se o time quiser mostrar o curso de cada pessoa, alguém precisa editar 30 cartões, e vai esquecer algum.

A solução do frontend moderno é o componente: um pedaço de tela escrito uma vez, que recebe dados e pode ser usado quantas vezes for preciso. Um cartão, um botão e um menu são componentes.

Parte C: um componente em JavaScript

Abra o arquivo componentes.html do mural no editor. Para ver a página, abra um segundo terminal (o + do painel do terminal) e rode um servidor local dentro da pasta do mural:

cd /workspaces/codespace-aula/mural-da-turma
python3 -m http.server 8000   # server = servidor: serve os arquivos da pasta no endereço da porta 8000

O Codespace avisa que a porta 8000 foi aberta: clique em Open in Browser (abrir no navegador), ou abra a aba Ports (portas) e clique no ícone de globo ao lado da porta 8000. Abre uma aba com o mural, porque o servidor mostra o index.html primeiro. Na barra de endereço dessa aba, acrescente /componentes.html no fim do endereço e aperte Enter. Para parar o servidor no fim, aperte Ctrl+C. O trecho importante é este:

function Cartao(pessoa) {
  return `<li><strong>${pessoa.nome}</strong> ${pessoa.frase}</li>`;
}

const pessoas = [
  { nome: "Ana", frase: "Gosto de café e de futebol." },
  { nome: "Bruno", frase: "Quero trabalhar com jogos." },
];

document.querySelector("#lista").innerHTML = pessoas.map(Cartao).join("");
  • function Cartao(pessoa): function quer dizer “função”. Esta é o componente. Recebe uma pessoa e devolve (return) o HTML de um cartão.
  • const pessoas: os dados, uma pessoa por linha. const vem de constant (constante).
  • pessoas.map(Cartao): map quer dizer “mapear”. Chama o Cartao uma vez para cada pessoa.
  • .join(""): join quer dizer “juntar”. Junta os cartões num texto só. innerHTML é o “HTML de dentro” da lista: é onde os cartões entram.

Agora faça duas mudanças e recarregue o navegador depois de cada uma:

  1. Mude o componente. Dentro do Cartao, troque ${pessoa.frase} por <em>${pessoa.frase}</em> (em = emphasis, ênfase: deixa em itálico). Todos os cartões mudam juntos, com uma edição só.
  2. Mude os dados. Acrescente uma linha com o seu nome na lista pessoas. Seu cartão aparece com o mesmo visual dos outros, sem escrever HTML.
Confira

Todas as frases ficaram em itálico, e o seu cartão aparece no fim da lista.

Essas mudanças eram só um teste. Para descartar e deixar o mural como estava, use o que você aprendeu no exercício 1: no primeiro terminal (o segundo está ocupado pelo servidor), rode git restore componentes.html.

O mesmo componente em React

React é a biblioteca de componentes mais usada no mercado. O mesmo cartão em React fica assim:

function Cartao({ nome, frase }) {
  return <li><strong>{nome}</strong> {frase}</li>;
}

<Cartao nome="Ana" frase="Gosto de café e de futebol." />

A ideia é a que você acabou de usar: uma função que recebe dados e devolve um pedaço de tela. O React usa o componente como se fosse uma tag nova, <Cartao />. Ferramentas como o Vite preparam esse código para o navegador, que no fim recebe HTML, CSS e JavaScript. E o código fica num repositório Git, com branches e pull requests, como você fez hoje.
